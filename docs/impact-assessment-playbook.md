# Change-impact assessment playbook

**Status: operating design for a reference implementation; synthetic data only.** Nothing in this document records an actual release, assessment, reviewer decision or parallel run. Figures quoted below come from `python -m crw program-demo --out runs/impact-doc-demo` (seed 11, 20,000 synthetic parties) and are labeled synthetic. The headline counts and verdicts are retained in `evidence/program-demo-summary.json`, regenerated by `scripts/build_program_evidence.py`; cite that file rather than copying numbers by hand.

## Problem and scope

A customer risk rating system changes regularly: a reference table is edited, an attribute value is reclassified, a rule or calculation is altered. A common control is to promote each change to a test environment and assess its impact before release: snapshot every party's tier before and after the change, remove parties whose tier is pinned by an override that the change does not govern, tabulate tier migration per segment, and summarize the result for senior reviewers.

The `crw impact` commands implement that assessment as a deterministic, repeatable calculation with explicit integrity checks. They do not decide whether a change should be released, do not establish that the observed migration is correct, and do not connect to any rating system. An adopter supplies the snapshots, the configuration and the human review.

## Inputs and their contract

| Input | Format | Contract enforced by the code | Failure behavior |
| --- | --- | --- | --- |
| Pre-change snapshot | CSV, UTF-8 (byte-order mark tolerated) | Columns `party_id`, `segment`, `tier`, `pinned` required; extra columns ignored. `party_id` and `segment` match `[A-Za-z0-9_.:-]{1,128}`. `tier` is a scale label or a declared code. `pinned` is one of `1/true/t/yes/y` or `0/false/f/no/n/blank`, case-insensitive; through the Python API rows must be objects and a null `pinned` means not pinned. One row per party. | Missing column, malformed identifier, unknown tier, unparseable flag or duplicate party fails the run with the row number. |
| Post-change snapshot | Same as pre | Same as pre | Same as pre |
| Tier scale (`--scale`) | JSON | `scale_id`; `tiers` ordered lowest first, at least two, unique; optional `codes`, an object mapping each tier to a unique code (for example `"LOW": 1`) that is not itself a tier label. | Unknown or duplicate tiers, duplicate codes, or a code equal to a label fail. Default: the illustrative four-tier reference scale. |
| Assessment config (`--config`) | JSON | `assessment_id`, `description`, `pre_label`, `post_label`, `exclude_pinned` (boolean), `segments` mapping each segment to `{"mode": "paired" or "aggregate_only"}`; optional `unknown_segments` (`error` default, or `include`) and `aggregates` per aggregate-only segment as `{"pre": {tier: count}, "post": {tier: count}}`. | Unknown fields, a non-boolean `exclude_pinned`, aggregates for a paired segment, negative or non-integer counts, or aggregate counts naming the same tier twice (by label and by code) fail. A row from an unconfigured segment fails unless `unknown_segments` is `include`. A row from an aggregate-only segment fails. |
| Change manifest (`--manifest`) | JSON | See [change manifest template](../templates/change-manifest.md). | Unknown `change_type`, unknown tier, duplicate expectation ID, `min > max`, an empty `segments`, `from` or `to` list, a non-positive `unexplained_tolerance.min_count`, an expectation naming a segment absent from the assessment, or `expected_aggregate` naming a segment without aggregates fail. |
| Prior assessments (`--history`) | `assessment.json` files from earlier runs | Same tier scale as the current assessment. | Different scale fails. |
| Standard-process matrix (`--standard`) | CSV `segment, pre_tier, post_tier, count` | Tiers as labels or codes; nonnegative integer counts (no decimals, no truncation); no duplicate cells. Omitted cells are treated as zero, so a nonzero-only export is acceptable. | Unknown tier, non-integer or negative count, or duplicate cell fails. |

Snapshots must be immutable for the duration of the run. The engine computes each file's SHA-256 before partitioning and again after the join, and fails the run if either hash changed; `inputs.pre_sha256` and `inputs.post_sha256` record the pre-run hashes. The check detects a modification, not its cause, and applies only to file inputs. Extract to a frozen location first so the check never fires.

The default configuration declares `SEGMENT_E` as aggregate-only without aggregates. Run without `--config`, any real snapshot therefore yields the integrity finding `aggregate_only_segments_without_aggregates`. Always supply a configuration written for the population under assessment.

## Commands

```bash
python -m crw impact assess \
  --pre extracts/rel-snapshot-pre.csv --post extracts/rel-snapshot-post.csv \
  --scale configs/tier-scale.json --config configs/assessment.json \
  --manifest configs/change-manifest.json \
  --history runs/impact/prev-1/assessment.json runs/impact/prev-2/assessment.json \
  --standard extracts/standard-matrix.csv --tolerance-abs 0 --tolerance-rel 0 \
  --z-threshold 3.5 --partitions 16 --strict \
  --register records/assessment-register.jsonl --recorded-at 2026-10-29T00:00:00Z \
  --out runs/impact/this-release

python -m crw impact sql --pre-table snap_pre --post-table snap_post --scope-table scope_release --out runs/impact-matrix.sql
python -m crw impact narrative-check --facts runs/impact/this-release/facts-pack.json --draft drafts/narrative.txt --require total.moved total.matched
python -m crw impact verify-register --register records/assessment-register.jsonl --anchor release-records/register-anchor.json
```

Paths are illustrative. `--manifest`, `--history`, `--standard` and `--register` are optional; each omitted input leaves its annex reading "not supplied". Defaults: `--min-history` 5, `--z-threshold` 3.5, `--tolerance-abs` 0, `--tolerance-rel` 0. `--recorded-at` has no default and is required with `--register`; it must be a timezone-aware timestamp and is stored in UTC. The temporary working directory for partitions is settable only through the Python API (`workdir`).

Without `--strict`, `assess` exits zero when the calculation completes, including when the verdict is `requires_explanation` or `MISMATCH`; automation must then read the `verdicts` and `integrity_findings` fields of the printed JSON. With `--strict`, it exits with status 2 on `requires_explanation`, `MISMATCH` or any integrity finding, after printing the result. In strict mode the outputs and any register entry are written before the nonzero exit, so the register records failing assessments as well. Contract failures, malformed input (including wrongly typed JSON fields), a rejected narrative in `narrative-check`, and a broken chain in `verify-register` also exit with status 2. Use `--strict` in any scripted release step.

## Outputs

| File | Content |
| --- | --- |
| `assessment.json` | Per-segment matrices and summaries, aggregate-only results, totals, integrity findings, input row counts and SHA-256, config digest, limits, `assessment_hash` |
| `manifest.json`, `expectations.json` | The manifest as supplied and its reconciliation (when `--manifest`) |
| `baseline.json` | Historical comparison (when `--history`) |
| `parity.json` | Cell-level parity with the standard process (when `--standard`) |
| `impact-assessment.md` | Standard report in fixed section order |
| `impact-assessment.html` | Standalone page: summary, population and exclusions (with an all-segments row), and matrices as tables; aggregate-only section and annexes as escaped preformatted text |
| `impact-matrix-long.csv` | One row per segment and cell: `segment, pre_tier, post_tier, count`, zeros included |
| `facts-pack.json`, `narrative-prompt.txt` | Inputs for an optional AI-drafted narrative; see [AI workflows](ai-workflows.md) |

`assessment_hash` is a SHA-256 of the canonical assessment payload, which contains no timestamps or run settings. Re-running on the same files and configuration reproduces it regardless of `--partitions`; a different hash means different inputs, configuration or code.

## Reading the report

| Section | What it shows | Questions to ask |
| --- | --- | --- |
| 1. Change summary | Config description, manifest identity, matched, moved, up, down; integrity findings in bold | Does the moved share match the scale of the change as described? |
| 2. Population and exclusions | Per segment: matched, unchanged, up, down, entrants, exits, excluded (pinned), pinned moved, pin changed, segment changed | Are entrants and exits explained by population movement unrelated to the change? Is any `Pinned moved` nonzero? Why did any party gain or lose a pin between snapshots? |
| 3. Tier migration by segment | One matrix per paired segment; rows are the tier before, columns the tier after; diagonal is unchanged; `Moved` is the row share off the diagonal | Which cells carry the movement? Do multi-tier jumps appear where the change should only move one tier? |
| 4. Aggregate-only segments | Net change per tier, population change, minimum movers | Is the lower bound within the manifest's `expected_aggregate` declaration? |
| Annex A | Migration, population (`POPULATION-ENTRANTS`, `POPULATION-EXITS`) and aggregate (`AGGREGATE-<segment>`) results; unexplained items by kind | Does every FAIL and unexplained item have a written explanation? |
| Annex B | Rates unusual against prior assessments | Is the history comparable to this change? |
| Annex C | Cell differences against the existing process | Are differences zero, within declared tolerance, or a defect? |
| Limits | Fixed statements of what the counts do not establish | Are these carried into the reviewer summary? |

Synthetic illustration: 19,759 matched parties; 545 moved (2.8%): 125 up and 420 down. 178 pinned parties were excluded, 80 entered and 63 exited the population. In `SEGMENT_A` the largest off-diagonal cell is `MODERATE` to `LOW` at 112 parties, 5.1% of that row. Matched, moved, up, down and excluded are in the `impact` block of `evidence/program-demo-summary.json`; the segment detail is in `impact-assessment.md` of the demo run. These describe the synthetic snapshots only.

Counting rules that matter when reading the numbers:

* A party in both snapshots is placed in its **post-change** segment. A segment change is counted in `segment_changed` but the party still contributes to the post-change segment's matrix.
* With `exclude_pinned` true, a party pinned on **either** side is excluded from the matrix, entrants and exits, and counted once in `excluded_pinned`.
* `Pinned moved` counts parties pinned on **both** sides whose tier differs. A party pinned on one side only is excluded and counted in `Pin changed`; its tier movement is not tested, because a pin applied or lifted between snapshots can legitimately change the tier.
* `Pin changed` is reported per segment and in the facts pack but is not an integrity finding. A nonzero count needs a reason (override applied or released during the test window) in the Section 2 commentary.
* Entrants and exits are reported by tier but are not part of the matrix or the parity check. They are reconciled in total against `expected_population` when the manifest declares it, and reported as unexplained otherwise.

## Verdicts and findings

| Output | Value | Meaning | Required action |
| --- | --- | --- | --- |
| Integrity finding | `pinned_parties_changed_tier` | At least one party pinned before and after moved tier. Pinned tiers are fixed outside the change, so this indicates an extract, override or logic defect. | Stop. Identify the parties, establish the cause, re-extract or fix, re-run. Do not explain away. |
| Integrity finding | `aggregate_only_segments_without_aggregates` | A segment configured aggregate-only has no counts. | Supply aggregates or remove the segment from the configuration with a recorded reason. |
| Expectations | `consistent_with_manifest` | Every migration, population and aggregate result passed, no unexplained item at or above tolerance, no integrity finding. | Proceed to review. This does not validate the expectations themselves. |
| Expectations | `requires_explanation` | At least one FAIL, unexplained item or integrity finding. Unexplained items carry a `kind`: `migration`, `aggregate_only_movement`, `undeclared_entrants` or `undeclared_exits`. | Follow the procedure below. |
| Expectations | `overlapping_expectations` | Pairs of expectation IDs that both claim at least one nonzero cell; such cells count toward both observed totals. Not a verdict input. | Confirm the overlap is intended; otherwise narrow `from`, `to` or `segments`. |
| Parity | `EXACT_MATCH` | Every cell equal; same segment set. | Record. |
| Parity | `WITHIN_TOLERANCE` | Every differing cell within the declared tolerance; same segment set. | Record each difference and its cause. |
| Parity | `MISMATCH` | A cell outside tolerance, or a segment present on one side only. | Follow the procedure below. |
| Baseline | flags | `modified_z_exceeds_threshold`: rate far from the historical median relative to its spread. `outside_observed_range`: history has zero spread (median absolute deviation 0) and the rate lies outside the minimum to maximum of prior rates. | Explain or note as a new kind of change. A flag is not a defect finding. |
| Narrative | `grounded` / `rejected` | Numeric grounding of a draft against the facts pack. | A rejected draft is discarded or rewritten, never edited to pass. |
| Register | `intact` / `broken`; `anchored` | Hash chain verification, optionally against an external anchor. `anchored: false` proves internal consistency only. | A broken chain is an incident. |

### When the verdict is `requires_explanation`

1. Read `integrity_findings` first. An integrity finding takes precedence over every expectation result.
2. For each FAIL, compare `observed` with `expected`. Determine whether the expectation was mis-specified (wrong tiers, wrong direction, bound derived from a different population) or the change behaved differently from its design.
3. For each unexplained `migration` item, locate the cell in Section 3 and extract the parties behind it from the snapshots in the approved environment. Trace at least one party per cell through the changed logic.
4. For `undeclared_entrants` or `undeclared_exits`, establish the source of population change (onboarding, closure, scope change) and declare `expected_population` in future manifests. For `aggregate_only_movement`, confirm the aggregates and declare `expected_aggregate`.
5. Record the explanation per item in the report's Annex A commentary. Distinguish "explained by the change, expectation incomplete" from "not explained".
6. If the manifest was wrong, do not edit it after the fact to obtain a consistent verdict. Record the original manifest, the reconciliation, and a separately versioned corrected manifest with the reason. Re-running with a corrected manifest is a new reconciliation, not a replacement of the first.
7. Escalate anything not explained to the change owner before release review.

### When parity is `MISMATCH`

1. Check `segments_only_in_automated` and `segments_only_in_standard`. Segments are compared by populated (nonzero) cells, so a configured segment with no parties that the standard export omits is not a mismatch; a segment with parties on one side only is.
2. Check tier vocabulary and count format: codes in the standard file are mapped through the scale; unmapped labels and non-integer counts fail before comparison.
3. For cell differences, compare the populations: pinned exclusion rule (either side versus one side), post-change versus pre-change segment, treatment of entrants and exits, duplicate handling, extraction time.
4. Classify each difference as a defect in the new engine, a defect in the standard process, or a definitional difference. Log it in the [parity test plan](../templates/parity-test-plan.md) defect log.
5. Agreement with the standard process does not establish that either is correct.

### Integrity findings and register breaks

Treat both as incidents under the [monitoring and incident plan](../templates/monitoring-and-incident.md): preserve the inputs and outputs, identify the affected assessment hashes, correct, re-run as a new assessment, and record the chain of events. A run that fails because an input snapshot changed during the assessment is handled the same way: re-extract to an immutable location and re-run.

The register is tamper-evident, not tamper-proof. An edited or reordered entry breaks verification. Deleting trailing entries leaves a shorter chain that verifies on its own; to detect that, keep an anchor `{"entries": n, "last_entry_hash": "..."}` outside the register (for example in the release record), update it after every append, and pass it with `--anchor`. A register that no longer matches its anchor reports `broken`. The register file has no locking; run one writer at a time.

## Parallel-run (shadow) adoption

The engine should not replace an existing assessment process on the strength of its own tests. Run both side by side and prove agreement cell by cell before relying on the new output.

| Phase | Activity | Exit evidence |
| --- | --- | --- |
| Plan | Complete the [parity test plan](../templates/parity-test-plan.md): scope, number of releases N, change types to cover, tolerance, defect process | Plan recorded before the first shadow release |
| Shadow | For each of N consecutive releases, run the existing process unchanged and `crw impact assess --standard` on the same frozen snapshots | `parity.json` per release; every difference classified |
| Extend | Compare entrants, exits and exclusions separately; these are outside `reconcile_matrices` | Recorded comparison per release |
| Decide | Assess against the exit criteria | Decision record by the accountable role |
| Retire | Keep the old process available, unused, for a defined fallback period | Fallback rehearsal evidence |

Tolerance: the default and recommended value is zero (`EXACT_MATCH`), because both processes count the same parties from the same files. A nonzero tolerance is justified only for a documented definitional difference, for example a known extraction-time gap, and must be set before the first shadow release. The per-cell allowance is `max(tolerance_abs, tolerance_rel * max(automated, standard))`.

N is set by the adopter. It should cover every `change_type` the program expects (value classification, rule, weight or threshold, reference data, population scope, logic) and at least one release with aggregate-only segments and one with a nonzero pinned population.

Exit criteria for retiring the old path:

* N consecutive releases with `EXACT_MATCH`, or `WITHIN_TOLERANCE` with every difference attributed to a pre-declared definitional cause.
* No open defect in the parity defect log affecting the new engine.
* Entrants, exits and exclusions agree for the same N releases.
* Generated SQL, if used, reproduces the engine's cells on the target database.
* Reviewers have read at least one full cycle of reports in the new layout.
* A fallback procedure exists and has been exercised.

Demo reference: `program-demo` executes the generated SQL on SQLite against the same synthetic snapshots and passes its cells to `reconcile_matrices` as the "standard". The result is `EXACT_MATCH` over 64 cells with 0 differences, and `sql-parity.json` records 44 nonzero cells identical (synthetic). This is two independent computations in one codebase agreeing on synthetic data; it is a template for the shadow comparison, not evidence for any existing process.

## Per-release checklist

| Step | Check | Evidence |
| --- | --- | --- |
| 1 | Change manifest written and versioned **before** deployment to test: migration bounds from a preview on a separate sample, population and aggregate-only bounds declared | `change-manifest.json`, preview output |
| 2 | Tier scale and assessment config reviewed for this population; aggregate-only segments have counts | Config digest in `assessment.json` |
| 3 | Pre snapshot extracted and frozen before deployment; post snapshot after; same extraction logic | SHA-256 in `assessment.json` |
| 4 | Scope table current for this release; SQL `checks` statement returns n = 0 on every row (SQL route) | Scope table version, checks output |
| 5 | `crw impact assess --strict` run with manifest, history, standard (during shadow) and register | Output directory, exit status |
| 6 | Integrity findings empty, or incident opened; any `Pin changed` explained | `assessment.json` |
| 7 | Expectations verdict recorded; every FAIL and unexplained movement explained | `expectations.json`, Annex A commentary |
| 8 | Baseline flags reviewed and commented | `baseline.json` |
| 9 | Parity verdict recorded; differences classified (shadow period) | `parity.json`, defect log |
| 10 | Narrative, if AI-drafted, passes `narrative-check` and human review | Check output, reviewer note |
| 11 | Register appended with `--recorded-at`; anchor updated in the release record; `verify-register --anchor` reports `intact` and `anchored: true` | `verify-register` output, anchor file |
| 12 | Report completed in the [standard skeleton](../templates/impact-assessment-report.md) and submitted to the accountable reviewer | Report, review decision recorded by role |

## Limits

* The assessment describes two snapshots. It does not establish that the change is correct, desirable or compliant.
* Expectation reconciliation tests movement against declarations; a manifest written to match observed results defeats its purpose.
* Overlapping expectations each count the same cell; observed totals are not additive across expectations. `overlapping_expectations` lists the pairs.
* `Pin changed` parties are excluded from the matrix and are not tested for movement.
* The register detects deleted trailing entries only against an anchor kept elsewhere, and has no locking.
* Aggregate-only segments are reconciled only on their minimum-movers lower bound; they are excluded from baseline comparison and parity.
* Single process, single node, local files. No scheduling, authentication, access control or orchestration. See [architecture](impact-automation-architecture.md).
