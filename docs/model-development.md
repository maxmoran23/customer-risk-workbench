# Model and policy development

This chapter defines a reproducible development method. Formula examples are original illustrations, not recommended production parameters. Read [architecture](architecture.md), [data contract](data-contract.md), and [limitations](limitations.md) before interpreting an experiment.

## Start with the decision

| Intended use | Relevant evidence | Invalid shortcut |
| --- | --- | --- |
| Prioritize customer reviews | Evidence coverage, review capacity, case relevance, queue outcomes | Call the score a probability of money laundering |
| Identify changed behavior | Historical baselines, observation support, known business changes | Treat every increase in volume as suspicious |
| Compare policy alternatives | Paired assessments, migration, reason changes, workload | Select the policy that generates the most high scores |
| Research a predictive challenger | Defined outcome, mature labels, proper partitions, held-out performance | Train on labels generated by the score being challenged |

Define the unit of assessment first: customer at a specified knowledge cutoff. Accounts and transactions are contributing records. If the same customer has many observations, those observations are not independent customers.

## Evidence, scale, and meaning

The source adapter must explain every normalized profile value. A value of `0.7` without a source, transformation, timestamp, and interpretation is an unsupported number. Profile evidence and behavioral measures can share a severity scale after transformation while retaining different meanings and different uncertainty.

For feature `j`, write its transformation as `s_j = T_j(x_j)`, with `0 <= s_j <= 1`. The transformation record should include the input unit, allowed range, direction, knots or cutoffs, treatment of absent observations, supporting rationale, and counterexamples. Do not infer that equal severity values have equal empirical risk unless evidence supports that inference.

Illustrative monotone ramp:

```text
T(x; a,b) = 0                     if x <= a
           (x-a)/(b-a)            if a < x < b
           1                     if x >= b, with b > a
```

This is a mathematical design option. Whether it is implemented for a particular feature is determined by the active policy schema and engine. A step transform creates abrupt behavior at boundaries; a ramp trades that discontinuity for a linearity assumption. Either choice needs boundary tests and a business rationale.

## Group-capped sum and maximum index

The architecture specifies group contributions:

```text
C_g = min(cap_g, aggregate_g(weight_j * s_j))
S   = sum_g(C_g), with configured caps bounding S to [0,100]
```

`aggregate_g` is either `sum` or `max`, declared in the policy. The reference policy uses maximum aggregation for geography, behavior, and evidence groups, and sums customer, product/channel, and context contributions. The maximum prevents overlapping windows from receiving multiple additive votes. Group caps limit one family from overwhelming the index. Neither choice proves that redundancy is solved. Similar measures can still count the same underlying fact across groups; review correlations, feature meaning, and common data provenance.

Worked calculation for a separate illustrative all-sum policy with fully observed severities:

| Group | Inputs | Uncapped contribution | Cap | Final contribution |
| --- | --- | --- | --- | --- |
| Profile | `12*0.5 + 8*0.25` | 8 | 20 | 8 |
| Behavior | `15*0.8 + 10*0.6` | 18 | 15 | 15 |
| Evidence change | `10*0.2` | 2 | 10 | 2 |

The constructed index is `8 + 15 + 2 = 25`. This arithmetic example is not a bundled policy claim. Capping explains why adding another correlated behavior signal may leave the final contribution unchanged. Explanations must show both the uncapped contributions and the cap effect; ranking raw contributions alone can misstate influence.

## Missing evidence and intervals

Missing values must remain distinguishable from observed zero. For a nonnegative monotone additive policy, one transparent bound assigns unknown severity `0` for the lower calculation and `1` for the upper calculation:

```text
L = score(observed severities, unknown severities=0)
U = score(observed severities, unknown severities=1)
```

This is a range of possible policy outputs under those unknown inputs. It is **not** a confidence interval, a posterior distribution, or an estimate of measurement error. It also does not include unknown defects in apparently observed data. Dependencies may make some combinations unattainable, so the envelope may be conservative.

The engine exposes the lower bound as `provisional_index`; it is not an imputed central estimate. `score` is non-null only when every configured factor is observed and no gate is active. Optional missing factors can leave a usable band when the entire interval lies within that band; `score` remains null. Required missing evidence, unconfirmed history when required by policy, or an interval crossing bands produces `REVIEW_REQUIRED`. The policy must explicitly declare whether complete history is required. A missing route input produces a separate `UNKNOWN` route state.

## Time windows and overlapping evidence

A rolling month, a lifetime aggregate, and the most recent transactions answer different questions. The shorter windows are nested in the longer ones. Treating them as independent corroborating observations exaggerates support.

| Window family | Interpretation | Failure mode to investigate |
| --- | --- | --- |
| Calendar duration | Recent activity within an explicit cutoff interval | Seasonality and short retained history |
| Last N events | Behavior across a fixed number of recent observations | Very different calendar spans for sparse and active customers |
| Lifetime | Available history since onboarding, only if complete | Retention truncation falsely described as lifetime |
| Current versus previous period | Change relative to an earlier baseline | Zero baseline, partial history, business expansion |

The implemented `flow_through` is an incoming/outgoing balance proxy. It does not establish transaction-level funds movement, sequence, circularity, or laundering. High balance can occur in payroll processing, treasury operations, settlement, and other lawful activity. A real tracing feature would require a different data contract and separate validation.

## Outcome design before model selection

Define the outcome before choosing logistic regression, a tree model, or any other learner. Required fields include unit, event definition, event date, label availability date, maturation horizon, adjudication method, and review coverage. A reviewed customer without an adverse finding is not automatically a known negative in an unreviewed population.

Keep these labels distinct: analyst escalation, investigation opened, report filed, confirmed policy breach, and externally established unlawful conduct. They have different meanings and different observation processes. A classifier trained on escalation predicts that process under its sampling and review conditions; it does not acquire a broader meaning from a better metric.

The synthetic research generator must have stochastic latent outcomes separate from deterministic policy outputs. Changing the score policy must not silently change the labels. This prevents a circular experiment in which a model receives excellent marks for reproducing the rule that created its target.

## Partition and fitting protocol

1. Freeze the target, observation cutoff, horizon, eligible population, and metric definitions.
2. Allocate customers to development, validation, and final evaluation populations before fitting transformations. For temporal claims, ensure chronological separation and exclude features unavailable at each historical cutoff.
3. Keep repeated observations of a customer within the permitted partition design. If evaluating returning customers, document that distinct estimand and temporal constraints rather than claiming unseen-customer generalization.
4. Fit preprocessing, imputation, encodings, feature selection, calibration, and thresholds on development/validation data only.
5. Lock the final evaluation set. Record how many times it has influenced a decision. Repeatedly tuning to it converts it into development data.
6. Compare against simple baselines and the current policy with paired customers and consistent inclusion rules.
7. Preserve the selected and rejected experiments, seeds, versions, reason for selection, and limitations.

## Challenger acceptance

A challenger should earn further evaluation through more than discrimination. Require a coherent target, stable comparisons, interpretable failure analysis, reproducibility, adequate subgroup support, bounded operational burden, and a plan for unavailable or changed inputs. A small improvement in an aggregate metric may be unhelpful if review workload doubles or an important low-support segment deteriorates.

Use [the experiment template](../templates/development-experiment.md) to specify acceptance criteria before results are seen. No universal acceptance value is supplied: the appropriate tolerance depends on the decision, error costs, prevalence, and evidence.

## Developer release evidence

The release evidence should include the exact policy, feature catalog, source/config/code hashes, fixture results, partition manifest, experiment results, limitations, and a reproducible command. These records establish what was run. They do not substitute for objective review or representative operational outcomes. The current source framework is summarized in [regulatory-map.md](regulatory-map.md).

The implemented supervised research contract and replayable logistic artifact are documented in [statistical-methods.md](statistical-methods.md). That interface is separate from the transaction-engine contract: an adapter must establish point-in-time feature meaning before constructing research rows. Research partition names and probability metrics must not be retroactively applied to the policy index.
